# Chen et al. 2025, CangLing-KnowFlow (knowledge-and-flow agent for RS)

## Problem
Automated RS systems are usually built for one task. General LLM agents can chain tools but hallucinate steps and fail on long, data-heavy EO workflows that run from preprocessing to interpretation. Fixed workflows are stable but cannot recover from runtime failures (Sec I).

## Approach
- Procedural Knowledge Base (Sec III-B, IV-A): a tool library (the full GDAL algorithm set wrapped as PDDL-style tools with parameters, preconditions and effects, plus four deep-learning tools: semantic segmentation, object detection, change detection, RS inversion) and 1,008 expert workflow templates over 162 RS tasks, stored as hierarchical DAGs. The 162 task descriptions were generated by Gemini 2.5 Pro; experts then wrote 2 to 10 abstract workflows per task.
- Dynamic Workflow Adjustment (Sec III-C): when a step returns an error or fails a quality metric (causes named include vague user extents, unexpected cloud cover, sensor noise, non-converging networks), the agent first looks for a stored repair rule, else asks the LLM, and edits the DAG by node replacement, node insertion or parameter change.
- Evolutionary Memory Module (Sec III-D): stores full execution traces; successful repaired workflows become new templates, terminal failures become IF-THEN repair rules (the paper's example inserts speckle suppression when a detector fails on SAR data).

## Data and benchmarks
KnowFlow-Bench: the same 162 tasks, each with two expert-annotated, fully parameterised ground-truth workflows (324 instances), split into simple and complex tasks (Sec IV-B). The paper does not describe the input imagery, sensors or regions used. Also tested on ThinkGeo (436 tasks, 14 tools). 13 LLM backbones from Mistral-7B and Llama3-8B to GPT-5 and Claude 4 Sonnet (Table I). Metrics: task success rate (TSR, result semantically and numerically correct against the reference with minimal human intervention), first-pass accuracy (FPA), number of tool calls (NTC) and number of human interactions (NI) (Sec IV-C).

## Key results
- Table I (simple / complex TSR): Claude 4 Sonnet 96.1 / 95.1 vs Reflexion 92.6 / 90.6; GPT-5 94.7 / 93.7; DeepSeek-R1 93.1 / 89.1; Llama3-70B 83.6 / 74.6; Mistral-7B 68.4 / 54.2. The full framework beats Reflexion by at least 4 TSR points on complex tasks for every backbone.
- Llama3-70B with KnowFlow (74.6 complex) roughly matches GPT-4 with ReAct (74.9), the authors' "force multiplier" argument (Sec V-D).
- Ablation with Claude 4 Sonnet (Table III, simple tasks): full model TSR 96.1%, FPA 79.2%, 6.8 tool calls, 0.8 interactions; removing the workflow library drops TSR to 88.7% and raises tool calls to 13.2; removing dynamic adjustment 91.5%; removing learning 92.8%.
- ThinkGeo transfer (Table II): TSR 20.3% vs 9.0% ReAct and 10.0% Reflexion with Claude 4 Sonnet; 16.8% with GPT-4. Absolute success is low outside its own benchmark.
- Even with the best backbone, the agent still needs about one human interaction per task on average (NI 0.8, Table III).

## Limitations
- Success is judged against expert reference workflows, not against field truth, and outputs carry no uncertainty.
- No hardware, run count or variance reported. In Table I most simple and complex score pairs share the same decimal and differ by a whole number (for example DeepSeek-R1 LLM+Tools TSR 83.4 vs 77.4 and FPA 62.7 vs 54.7), an unusual pattern for measured rates, and Table II contains implausible tool-call entries (about 1250 and 1350), so the numbers should be cited with caution.
- Relies on large hosted or 70B-class LLMs for the headline numbers; no CPU or offline deployment.
- Benchmark inputs, sensors and regions are not described; benchmark and code not released.
- No Indian or flood-specific evaluation; flood inundation appears only as an example template name.

## What it means for EvidEO
- Adopt: the result that removing the workflow library is the biggest loss supports EvidEO's fixed, templated flood and crop pipelines instead of free planning.
- Adopt: log runtime failures (no scene, cloud above limit, empty mask) as typed events; they become abstention reasons shown to the user.
- Beat: KnowFlow aims for task completion; EvidEO's added value is telling an official how much to trust the number and declining when it should.

## Full-text check (2026-10-14)
Ingredients (paper's own system as built and evaluated):
- C1 Calibrated per-answer confidence: No. No confidence output; "uncertainty" in Sec III-C refers to runtime failures, not answer probability.
- C2 Threshold abstention with a next step: No. A terminal failure ends the run (Algorithm 1) and is turned into an internal repair rule, but there is no confidence line and no user-facing next step; human interactions (NI) are counted as a cost, not designed as abstention.
- C3 Scene receipts that reproduce: part. Every run stores a full execution trace with actions, intermediate outputs, failures and repairs (Sec III-D), but answers do not cite scene IDs or dates and no re-run reproducibility is shown.
- C4 SAR chosen automatically under cloud: No. Cloud cover is named as a failure cause and a SAR repair rule is given as an example, but no automatic optical-to-radar switch is built or evaluated.
- C5 CPU or offline deployment: No. Hardware not reported; small backbones (7B, 8B) are evaluated but with much lower success, and no offline claim is made.
- C6 Plain-language questions for non-experts: No. Inputs are task goals for expert workflows; no non-expert framing or evaluation.

What the abstract-level entry got wrong or left unconfirmed:
- The 96.1% headline is the simple-task TSR; complex tasks reach 95.1% (Table I).
- The DeepSeek-R1 value 93.1% is simple tasks; complex is 89.1%, vs Reflexion 87.8 / 84.8.
- The 162 task descriptions were LLM-generated (Gemini 2.5 Pro), with experts writing the workflows.
- ThinkGeo transfer success is only about 13 to 20% (Table II), not mentioned before.

Novelty implications: one part (C3). It does not threaten the "no more than two" claim; its replanning and failure-rule memory are closest to EvidEO's typed abstention reasons, but they serve the agent, not the user.
